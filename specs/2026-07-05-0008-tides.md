# 0008 — Tides (marées)

- **Status:** Accepted
- **Date:** 2026-07-05
- **Authors:** Hadrien Mary (+ Claude)
- **Relates to:** [0001 §6 feature spec](2026-06-27-0001-foundation.md) (extends it —
  tides were a non-goal there), [0004 realtime scraper](2026-06-27-0004-realtime-scraper.md)
  (the forward-growing-accumulator pattern this reuses), [0005 multi-buoy](2026-06-27-0005-multi-buoy.md).

> Add **tide (marée)** information to Olatu, in both the real-time banner and the
> time-series charts, so a surfer/sailor can read at a glance: the next high/low tide
> and countdown, where we are in the cycle (rising/falling, near high/low), and the
> **marnage** (tidal range) — is it a big tide or not. Reference studied and partly
> ported: the sibling project `wave-monitor` (`scripts/sync-tides.ts`, `src/lib/tides.ts`).

---

## 1. Why

Wave height/period/direction is only half of what the sea is doing. Tide state drives
where and when it's surfable, and on this coast people think in tides constantly. Olatu
already answers "how big, from where, how warm"; this adds "and the tide is doing X".

Foundation §1 listed *forecasting* as a non-goal. Astronomical **tide predictions** are a
deliberate, bounded exception the owner requested — they are deterministic ephemeris, not
a wave/weather model, and are a standard, expected marine-page feature.

## 2. Decisions

1. **Source = api-maree.fr** (`/water-levels`), the same API `wave-monitor` uses. Upstream:
   **IFREMER / PREVIMER** harmonic components (via Sextant), **CC-BY**. Auth is a 32-hex
   `key` query param. Free tier: window **J−30 … J+30**, `step` ∈ {1,5,10,15,20,30,60} min,
   **≤ 1500 points/request**, **360 requests/hour**. There is **no** high/low or coefficient
   endpoint → we derive extrema ourselves.
   - *Consequence:* tides exist only for a **rolling ~±30-day window** (extended forward by
     a forward-growing accumulator, see §3). History older than that has no tide data →
     the UI shows an empty-state, exactly like sea-temperature already does before its
     accumulation start.
2. **"Big tide" framing = marnage in metres only** — no French *coefficient de marée*. A
   neap↔spring **metre** fill bar answers "big or small" without any Brest/coefficient math.
3. **Charts = a dedicated, synced tide panel** plotting **marnage (tidal range, m) over
   time** on the Y axis — a slowly-varying spring↔neap signal that reads at any zoom and
   accumulates with the tide history. *(Revised 2026-07-05: the first cut plotted the raw
   water-level curve with ▲/▼ PM/BM markers, capped to ≲30-day windows; that was unreadable
   past a few days and hid the accumulating history. The live water-level phase now lives
   only in the banner arc; the chart is marnage-over-time, no span cap.)*
4. **Storage = the HF bucket `hadim/olatu`** (like every other tier). The published tier is
   `<campaign>/data/tides.json`; the raw extrema **accumulator** is
   `<campaign>/raw/<campaign>_tides.csv`, forward-growing, mirroring the reel.

**Key handling.** The API key is **ingest-only** and never enters the client bundle — the
webapp only ever reads the pre-derived static `tides.json`. In CI the key is the GitHub
secret `API_MAREE_KEY` (a step back from keyless OIDC, but confined to the data job and
never shipped). Locally it comes from the env. A missing key is **non-fatal**: the tide
step is skipped and the rest of the refresh proceeds (keyless dev still builds).

## 3. Data model & pipeline

New ingest step `ingest/tides.py`, run from `update.py` **after scrape, before build**:

1. **Fetch** `/water-levels` for the buoy's `tide_site` over **J−30 … J+30** at `step=10`
   min, in **10-day chunks** (1440 pts < 1500 cap), `tz=UTC` (so returned times are UTC —
   Olatu's storage convention; the webapp renders Europe/Paris as usual). De-dup the seam
   point shared between chunks.
2. **Derive extrema** (port of `sync-tides.ts findExtrema`): a **W-sample slope test**
   (W=3 ≈ 30 min at step=10) robust to the API's 3-decimal plateaus near peaks, then a
   **parabolic sub-sample** of the exact time/height through the three neighbours, then a
   same-kind de-dup within 90 min. Output: `(datetime_utc, height_m, kind∈{high,low})`.
3. **Coalesce** into `raw/<campaign>_tides.csv` with a **replace-window merge**: keep old
   events *outside* the freshly-fetched [J−30, J+30] window, replace everything *inside*
   with the new extrema. Consecutive fetch windows always overlap (60-day windows, gated
   ≈ every 10 days), so no gap forms and the region that scrolls out of each new window is
   frozen into permanent forward-growing history. Self-healing for the recent past.
4. **Emit** `data/tides.json`:
   ```json
   {
     "site": "socoa", "site_label": "Socoa (Saint-Jean-de-Luz)",
     "timezone": "Europe/Paris",
     "generated_at": "2026-07-05T…Z",
     "range_ref": { "neap": 1.2, "spring": 4.5 },
     "source": { "provider": "api-maree.fr", "upstream": "IFREMER / PREVIMER",
                 "license": "CC-BY", "credit": "Hauteurs d'eau diffusées par api-maree.fr,
                 calculées à partir de composantes harmoniques IFREMER / PREVIMER.",
                 "url": "https://api-maree.fr" },
     "events": [ { "t": 1720000000, "h": 0.84, "k": "low" }, … ]
   }
   ```
   `t` = **epoch seconds UTC** (matches the columnar tiers' `t`); `h` = metres; `k` =
   `high|low`. `build.py` adds `"tides": "tides.json"` to `manifest.tiers`.

**Fetch cadence / gate.** Only fetch when the accumulator's **forward horizon < 20 days**
(stateless, quota-polite): after a fetch we hold +30 days, so it re-fires ≈ every 10 days
per buoy — 3 buoys × ~6 chunked requests ≪ 360/h. The accumulator always brackets "now",
so the banner is always populated between fetches.

**Per-buoy config** in `ingest/schema.py` `BUOYS`:
- `tide_site` — the api-maree.fr site id. **To validate against `/sites`** once a key
  exists (best guesses: 06403 → `socoa`, 06402 → `boucau-bayonne-biarritz`,
  03302 → `arcachon-eyrac`). A bad/absent site → fetch fails → empty-state, not a crash.
- `tide_range_ref {neap, spring}` (metres) — the neap→spring envelope for the magnitude
  bar. Regional constants (Basque ≈ {1.2, 4.5} like wave-monitor; Arcachon ≈ {1.3, 4.6}),
  **not** derived from the J±30 window (one spring-neap cycle would mislabel a monthly max).

**Published-tier size.** `tides.json` publishes the full accumulator; it starts at ~J±30
(≈ 240 events, ~8 KB) and grows ~1460 events/yr (~15 KB/yr). Revisit a rolling cap
(e.g. last N years) if it ever gets heavy — a one-line change, no format break.

## 4. Runtime (webapp)

`webapp/src/lib/tides.ts` — a **framework-agnostic** port of wave-monitor's pure functions:
- `parseTides(json)` → `{ meta, rangeRef, events: {t(ms), h, kind}[] }`.
- `tidePhase(events, now)` → previous/next extremum, `rising`, `progress` (fraction of the
  half-cycle), interpolated `height` (**raised-cosine** `h = prev + (next−prev)·(1−cos(π·p))/2`),
  `amplitude` (marnage of the current half-cycle), `msToNext`, coarse `label`
  (near-low / rising / near-high / falling). `null` when `now` isn't bracketed.
- `reconstructCurve(events, xmin, xmax, stepSec)` → samples the raised-cosine between
  consecutive extrema for the chart panel.
- `tideMagnitude(range, ref)` → `{ t∈[0,1], label }` in **metres** (no coefficient).

**Reconstruction is the raised-cosine** (the theoretical half-sine tide shape), *not* the
literal predicted curve — nearshore shallow-water asymmetry (Adour, Arcachon lagoon) is not
modelled. Documented simplification; acceptable for these regular semi-diurnal stations.
Ship extrema only (light + accumulates); reconstruct in the browser.

### 4.1 Banner (`TideStrip` in `CurrentConditions`)
A compact, single responsive band at the bottom of the current-conditions card (hairline-
separated; stacks on mobile):
- a **half-sine arc with a marker riding it** (rising/falling + where-in-cycle — the
  wave-monitor signature, in Olatu tokens),
- the **phase** word (Rising/Falling/Near high/Near low → montante/descendante/étale),
- the **next** extremum with a **live countdown** ("Next ▲ 14:32 · in 2 h 08", ticked by
  `useNow`) and the previous one,
- **marnage** in metres + a **neap↔spring metre fill bar**.
Empty-state (no tide data / `now` unbracketed): the strip hides gracefully.

### 4.2 Chart (dedicated tide panel in `TimeSeries`)
A new synced uPlot panel, special-cased because its series is **external** (built from
`events`, not the wave `Columnar`):
- Y = **marnage** (tidal range, m): one point per extremum valued at the |Δheight| to the
  previous one (`marnageSeries`), a **zero-based** filled line. A > 12 h gap in the extrema
  breaks the line. Smoothed by the Raw/Light/Strong control like the wave panels.
- shared x-axis + crosshair; the hover card + accessible summary show the marnage of the
  bracketing cycle (`marnageAt`); an **empty-state overlay** (`chart-empty` + `emptyKey`)
  only where the window has no tide data — **no span cap**, so the full accumulating history
  shows like the other panels. The live water-level *phase* lives in the banner, not here.
