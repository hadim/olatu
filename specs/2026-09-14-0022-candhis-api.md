# 0022 — CANDHIS API: the sanctioned feed, five years of sea temperature, an automatic archive

**Status:** Accepted
**Date:** 2026-09-14
**Supersedes / relates:** revises [0004 — Realtime scraper](2026-06-27-0004-realtime-scraper.md)
§1 (where the realtime feed comes from), §6 (cadence) and §7 (the archive refresh recipe). Its
merge safety (§4) and validation (§5) are **kept unchanged and shared** by both feeds. Failure
classification per [0020 — Outage tolerance](2026-09-08-0020-outage-tolerance.md); the gap-aware
window is the lesson of [0012 §3.1](2026-07-24-0012-wind.md) / LEARNINGS 2026-09-03.

## 1. Why

Until today the only way to read CANDHIS was to scrape `campagne.php` (0004 §1). It worked, and
it cost us three things:

- **A fixed 48 h window.** The HTML table shows the last ~48 h and nothing else, so any pipeline
  outage longer than that is a permanent hole in the one series (sea temperature) that has no
  other source.
- **Fragility we can't fix.** On 2026-09-10 the same URL served the table at 13:37 and the
  "choose a campaign" page at 14:17 (0020 §5). A page layout is not a contract.
- **A manual archive.** The QC'd archive is re-seeded by hand through the `teleFic.php` form,
  then the CI cache key is bumped (0004 §7, done 2026-09-11) — or CI silently keeps building
  from the old copy.

On 2026-09-14 Cerema answered the owner's request with a key to the **CANDHIS API v1**
([user doc](https://candhis.cerema.fr/doc/04_Candhis_API_v1_Utilisateur.pdf)): 150 requests/day,
12 months of data per request.

## 2. What the API really is (probed 2026-09-14, ~40 requests)

`GET https://candhis.cerema.fr/API/v1/<function>.php?…` with an `Authorization: <key>` header;
JSON `{apiVer, success, message, nbLig, entete, results}`, every value a string.

| Question | Finding |
|---|---|
| Does realtime (`getCampTR`) match what we scrape? | **Yes, exactly.** 0 value diffs over the 10 461 scraped 2026 rows of 06403 / 06402 / 03302. The API omits rows that are empty in every column (150 on 03302, 1 on 06402), which carry no information. |
| How far back does realtime go? | **The whole realtime history, not 48 h.** 06403 and 03302 from 2021-05-21, 06402 from 2021-06-21; 2020 and earlier are empty. ~15–17 k rows/year, sea temperature in > 99 % of them. |
| Does the archive (`getCampTD`) match `*_arch.csv`? | **Yes**, value for value (2026-08-01 checked), plus a filled `QUALITE` that the CSV export leaves empty, repeated as a duplicate trailing column (74 cells vs 73). |
| Window semantics | `dateFin` is **exclusive** (`2026-09-06`→`2026-09-08` = 96 rows, 06 00:00 → 07 23:30). One request is capped at 12 months. |
| "No data" | HTTP 200, `success: true`, `nbLig: 0`, message `Pas de données…`. The PDF says `success: false`; it isn't. |
| Errors | JSON bodies on 400 / 401 / 404 / 405 / 423 (IP banned) / 429 (daily quota). |
| Quota visibility | None — no header reports what is left. We count our own calls. |
| Speed | ~0.1 s for a few days; 1–3 s and ~1.3 MB for a full year. |
| Timestamps | `YYYY-MM-DD HH:MM`, no zone — UTC, since they match the (UTC) reel exactly. |
| `getCampListeTR` (all buoys, one call) | Returns only the latest **hourly** value per campaign and took 6 s. Not used. |

At the time of the probe all three buoys had been silent upstream since **2026-09-08 12:00 UTC**
(API and HTML agree) — the API does not change freshness, only how we read it.

## 3. Decision

### 3.1 Realtime: the API first, the HTML table as fallback

`ingest/candhis_api.py` fetches `getCampTR` and hands the rows to **`scrape.merge_rows`** — the
merge extracted from `scrape()` — so both feeds write the same `Candhis_<c>_<YEAR>_reel.csv`
through the same `validate_rows`, coalesce, never-shrink and atomic write. `build.py` cannot tell
which feed wrote a row, and does not change.

- **Gap-aware window.** A routine fetch asks from the date of the **newest reading we hold**
  (never less than the last 2 days, never more than 12 months) through tomorrow (exclusive). One
  request refills any pipeline outage up to a year; a missed run costs latency, never data.
- **Feed policy** (`update --feed auto|api|html`, default `auto`): the API on its slots (§3.2)
  when `CANDHIS_API_KEY` is set, the HTML table otherwise, **and** the HTML table whenever the API
  raises `FeedUnavailable` — transport fault, 5xx, non-JSON body, or 429. A hard API error (a
  4xx, a changed header, a bad row) stays red, per 0020: it is ours.
- **The scraper stays** (owner, 2026-09-14): it is the fallback, and the whole plan if Cerema
  does not raise the quota.
- The `feed` column of the run summary says which one ran: `api` · `html` · `html (quota)` ·
  `html (api down)` · `unavailable`.

### 3.2 Cadence: every 15 minutes, the API as often as the quota allows

- The refresh cron goes from `*/30` to **`*/15`** (owner).
- One realtime call per buoy per run would be 96 × 3 = **288/day** against a 150/day quota. So
  the API is called on runs whose minute-of-day slot (floored to the 15-min step) is a multiple
  of **`CANDHIS_API_INTERVAL_MIN`**; the other runs read the HTML table. The workflow reads the
  repo variable of that name and defaults to **60** (72 realtime + 3 archive ≈ 75/day, leaving
  half the quota to local runs and backfills); the code defaults to 15 (API every run).
- The slot is **stateless** on purpose: a delayed or dropped cron only moves the next API call,
  and the gap-aware window catches up.
- After the first 429 in a process, **no further calls** are made (the quota is per key). A
  partner we are asking for more quota should not see us keep knocking.
- **Quota request:** 500/day — the 288 routine calls, the daily archive, retries, manual
  dispatches and local runs, with ~1.7× headroom (each extra buoy adds 96/day). Once granted, set
  `CANDHIS_API_INTERVAL_MIN=15`; nothing else changes. If refused, leave it at 60.

### 3.3 Backfill the realtime history — sea temperature from 2021

One-time `pixi run candhis --all --since 2021-01-01` (6 requests per buoy) writes
`Candhis_<c>_2021…2025_reel.csv` and densifies 2026 (06403: 3 598 → 10 185 rows). 0004 §4's
archive-preferred coalesce is what makes this safe: archive columns keep winning wherever the
archive has them; realtime fills sea temperature and the archive's own gaps.

- Effect on the 06403 build: `coverage.sea_temperature_c.start` **2026-06-25 → 2021-05-21**.
- The old rule "sea temperature has no history, it only accumulates forward" now reads: history
  from mid-2021, none before.
- `snapshot_reel` backs up only the reels a refresh can still change (this year; also last year
  during January). The backfilled past years are frozen, and copying five of them into a dated
  key every day would be pure churn.

### 3.4 The archive refreshes itself

- Once per UTC day per buoy — recorded in `raw/candhis_api.json` (`{"archive_checked": date}`),
  pulled and uploaded with the reels — `getCampTD` fetches the **current year**, plus **last
  year through February** (QC'd rows land weeks late), and coalesces it into
  `Candhis_<c>_<YEAR>_arch.csv`: a fetched cell wins only when non-null, the union cannot shrink,
  the existing column order is kept, and values stay the API's strings — so the file remains
  byte-comparable with a manual export.
- Only the archive files that **changed** are uploaded, **by name** (`batch_bucket_files`), never
  by a glob sync: CI restores the archives from a cache, and a sync could push a stale restored
  copy back over a newer one.
- `pull` re-syncs those live archive years from the bucket on **every** run, after the usual
  "archive missing" pull, so CI's cached copy can never rebuild the tiers from a stale archive.
  The cache key (`candhis-raw-v2`) now only needs a bump when a **past** year is re-seeded by
  hand. This replaces 0004 §7's recipe for the current year.
- Failures: an outage or a spent quota logs a warning and leaves the state unwritten, so the next
  run tries again; a format error fails that buoy red at the end of the run, but its live feed,
  build and upload still happen first.

## 4. Consequences

- **The quota is a shared resource.** Local `pixi run update` / `pixi run candhis` count against
  the same 150/day as CI; `pixi run candhis` prints how many calls it made.
- **HF bucket:** uploads and the OIDC exchange run twice as often. The exchange has tripped
  429s at `*/30` before (retried); watch it.
- **Météo-France DPObs:** the 66-min tail re-probe doubles in frequency — ~44 calls/hour per
  station, far under the 100/min limit.
- **Webapp copy:** "Olatu refreshes every 30 minutes" becomes 15.
- `CANDHIS_API_KEY` is an ingest-only secret (GitHub Actions + local `.env`), never in the client.
